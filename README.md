# Bitburner Orchestration Benchmark

> A public benchmark measuring how well LLMs **orchestrate** teams of coding subagents — not how well they code alone.

## What This Is

Each benchmarked model plays the role of an **orchestrator**: a manager that directs a team of **subagent** LLMs to play [Bitburner](https://github.com/bitburner-official/bitburner-src) for 24 real-time hours. Orchestrators don't write code or touch the game. They only decide which subagents to spawn, kill, and instruct. Subagents write the Netscript that actually plays.

The leaderboard ranks orchestrators by the total in-game money their team accumulates.

## Why

Software engineering with AI is moving from single-agent code generation toward multi-agent orchestration. Existing benchmarks measure how well a model codes. This one measures how well a model *manages a team that codes*.

## How It Works

- **20-minute wall-clock runs.** Real time, no tick acceleration. 20 minutes is the canonical ranked duration; a separate 24-hour *endurance* config measures long-horizon behaviour and is reported separately, never mixed into the same column.
- **Pinned game state.** Bitburner is forked and locked to a specific commit with a pinned RNG seed.
- **Fair rosters.** Every orchestrator in a given cycle picks subagents from the same curated pool of models.
- **Blind orchestration.** The orchestrator sees only what its subagents report back, plus periodic snapshots of game state (24 per run, whatever its length). No direct game access, no wiki, no guides.
- **Batch results.** Each run produces a Git commit with delegation logs, generated scripts, and stats. A daily aggregator builds the static leaderboard.

## Scoring

**Primary:** Total in-game money at the end of the canonical 20-minute run.

**Secondary (observational, not ranked):** BitNodes completed, augments installed, time distribution across BitNodes, emergent strategies.

## What Each Run Produces

- `summary.json` — final stats.
- `delegations.json` — every instruction the orchestrator sent and every result subagents returned.
- `scripts.json` — all code generated by subagents.
- `snapshots.json` — periodic game state (24 per run).

These are committed to an `orchestrator/<model>` branch. The aggregator builds the public leaderboard from them.

## Deploy (Cloudflare Pages)

The leaderboard is a static site deployed by a daily GitHub Action.

**Pipeline:**

1. Each `orchestrator/<model>` branch holds that model's `results/<run_id>/` artifacts.
2. `.github/workflows/aggregate.yml` runs daily at 04:00 UTC (and on `workflow_dispatch`). It harvests `results/` from every `orchestrator/*` branch, runs `aggregator/build.ts`, and force-pushes the generated `pages/` contents to the `results-published` branch.
3. **Cloudflare Pages watches `results-published`** and serves the deploy.

**Cloudflare Pages setup (one-time, dashboard):**

1. Cloudflare Dashboard → Workers & Pages → **Create** → **Pages** → **Connect to Git**.
2. Pick this repo. Production branch: **`results-published`**.
3. Build command: *(leave empty — the artifact is already built)*. Build output directory: **`/`**. Root directory: *(leave empty)*.
4. Save & deploy. The first deploy populates after the next aggregator run; trigger it manually via Actions → `aggregate` → Run workflow.

The repo's branches stay clean: `main` carries the harness, `orchestrator/*` carry run artifacts, `results-published` carries only the deploy output. Don't merge `results-published` anywhere — it's an artifact branch.

## Methodology Notes

- **Why not expose the seed to the orchestrator?** Telling the orchestrator that the run is deterministic risks measuring seed-specific overfitting instead of general orchestration strategy. The seed is pinned for reproducibility across runs, but the orchestrator is told nothing about it.
- **Why forbid wiki access?** Bitburner has extensive public strategy wikis. If subagents could read them, the benchmark would measure retrieval skill, not reasoning or orchestration.
- **Why batch and not live?** Minimum attack surface, maximum reproducibility. Every result is a Git artifact.
