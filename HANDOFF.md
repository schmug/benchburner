# HANDOFF.md — Brief for Claude Code

You are building the backend harness and repo scaffolding for the Bitburner Orchestration Benchmark. Read `CLAUDE.md` and `SPEC.md` before writing any code.

## Your Goal

Produce a working harness that can execute the **First Milestone Acceptance Criteria** in §13 of `SPEC.md`:

> A single invocation of the harness with one orchestrator, one subagent in the roster, and duration reduced to 1 hour for smoke testing, produces: a populated SQLite DB, valid JSON exports, a `summary.json` with a real `final_money` value, no orchestrator prompt leakage of seed or game identity, and a git commit on the test branch.

Ship this before worrying about multi-model parallelism, polish, or fancy dashboards.

## Build Order

1. **Repo scaffolding**: create the directory structure from `CLAUDE.md` §"Repository Structure". Add empty `README.md` stubs in each module folder.
2. **Inference adapter interface** (`harness/inference/`): define the `InferenceAdapter` interface (SPEC §6). Implement `OllamaAdapter` first, then `HTTPAdapter`. Add a `models.yaml` loader.
3. **In-memory bus** (`harness/bus/`): simple typed pub/sub. No external queue. Channels: `instructions`, `results`, `snapshots`, `executions`.
4. **SQLite storage** (`harness/storage/`): schema from SPEC §4. Migration script. Writer functions for each table. JSON export functions.
5. **Bitburner integration** (`harness/game/` + `bitburner/`): vendor or submodule the fork. Implement script-submit, script-run, and game-state-read. Add the minimum fork patches needed (seed injection, state export). Document patches in `bitburner/patches/README.md`.
6. **Subagent worker** (`harness/subagent/`): consumes instructions from the bus, calls inference, returns results. Enforces token budget and timeout.
7. **Orchestrator loop** (`harness/orchestrator/`): polling-interval timer. Assembles input JSON per SPEC §3.1. Calls inference. Parses JSON output, dispatches actions to the bus. Logs to storage.
8. **Snapshot timer**: hourly game state pull → bus.
9. **Run entry point** (`harness/index.ts` or equivalent): loads `config/run.yaml`, boots the game, wires up all the pieces, runs for `duration_hours`, dumps JSON, commits.
10. **Aggregator** (`aggregator/`): reads run summaries across branches, produces `leaderboard.json` and basic HTML for `pages/`.
11. **GitHub Actions** (`.github/workflows/`): a run-trigger workflow and an aggregator workflow. Self-hosted runner.

## Key Decisions to Make

Resolve these as you build. Leave a comment or module-README note when you do.

- **RNG seed injection into Bitburner.** Likely a small patch to the fork's RNG initialization. Find the right spot and document it.
- **Subagent concurrency model.** Worker pool, async tasks, or child processes? Default to async tasks within the main process unless inference latency demands otherwise.
- **Delegation history compression.** Once history is long, the orchestrator's context window gets tight. Default: keep last 10 cycles verbatim, plus a rolling summary of older cycles generated by the orchestrator model itself (piggyback on its normal calls).
- **Game-to-harness communication.** Prefer Bitburner's Remote File API. Patch the fork only where RFA is insufficient.

## Things to Avoid

- **Do not** build a live HTTP API for the harness. It runs as a batch job.
- **Do not** expose the seed, the game name ("Bitburner"), or scoring details in the orchestrator prompt. See SPEC §3.3.
- **Do not** hard-code model names anywhere outside `config/models.yaml`. Everything is pluggable.
- **Do not** add retries to the 24h window on failure. One attempt per cycle. Log failures honestly.
- **Do not** skip the JSON exports from SQLite — they're what Pages consumes and what makes runs diff-able in Git.
- **Do not** design monetization features speculatively. This is a research artifact first.
